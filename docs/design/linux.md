## 2. The blockers: the brief's list verified, and the rest

### 2.1 The five in the brief

All five are real. Two of them change shape on inspection.

- **S48 — `JEVLIKE_ROOT` / `OPENJEV_DIR`.** `jev/server.py:61–66`, as filed.
  The failure is honest but late: `_jevlike()` checks
  `JEVLIKE_ROOT.is_dir()` before importing, so on Linux the error is a
  `RuntimeError` naming the variable rather than a bare import failure —
  but it arrives on the first `choose`, after `/health` has said 200 and
  after a graph has spent its first steps. *observed.*
- **jevlike is out of tree.** It is a real public upstream with its own
  history, so it does not need to become a vendored copy or a package we
  own: it can be a **declared input by revision** (§3, R5). What is *not*
  upstream is the checkpoint — `runs/synthetic.pt` is gitignored in that
  repo. The undeclared dependency is really two: the code (declarable) and
  a 169 KB artifact (ours to keep). *observed.*
- **torch.** nixpkgs `python3Packages.torch` is 2.13.0 from source, noted in
  its own file as "2+h with 2 cores, ~15m with a big-parallel builder";
  `cudaSupport`/`rocmSupport` follow `config`, `vulkanSupport` is false.
  This box runs 2.14.0+cpu. *documentation + observed.* The consequence
  for training is in R9.
- **Playwright.** nixpkgs `playwright-driver` and `python3Packages.playwright`
  are both **1.63.0 today — exactly the pin in `requirements.txt`** — and
  `playwright-driver.browsers` takes `withChromium/withFirefox/withWebkit/
  withFfmpeg/withChromiumHeadlessShell` overrides; the python package
  carries a `driver-location.patch` that points it at the store copy of the
  driver. *documentation.* One thing on our side is wrong for that world:
  `_chromium_installed()` globs under the venv's own
  `playwright/driver/package/.local-browsers`, **ignoring
  `PLAYWRIGHT_BROWSERS_PATH`** (`service.py:1193`), while the launch honours
  it because line 60 only `setdefault`s. So under Nix `/health` would report
  `chromium_installed: false` for a browser that launches. *observed in
  code; the Nix consequence is reasoned.*
- **`bin/hoot.ps1`.** Already ruled unsalvageable with conditionals (B2c;
  Decisions, "The launcher cannot be made POSIX"). The things it owns that
  the POSIX sibling must own too, verified from the file: start order
  (router → shim → face, because the face's registration reads the token the
  shim writes), the three waits (600 s / 90 s / 420 s), idempotent `up`, the
  Open WebUI environment (§2.2 item 5 lists it), the `loader.js` rewrite
  with `SHIM_ORIGIN` and the live `/jev` probe, the skin copy, `stop` in the
  reverse order with the shim last, `status` with both model lists, `setup`
  = `setup-bonsai2.ps1` + `eidolon ext dir`. *observed.*
- **XDG is reasoned, not observed.** It is now *documentation*-grade for the
  mapping and still *hypothesis* for the runtime. The vendored
  `dirs-6.0.0/src/lin.rs` is: `cache_dir` = `$XDG_CACHE_HOME` if absolute
  else `~/.cache`; `config_dir` = `$XDG_CONFIG_HOME` if absolute else
  `~/.config`; `data_local_dir` = `data_dir` = `$XDG_DATA_HOME` if absolute
  else `~/.local/share`. `jev/_paths.py` mirrors the first exactly. What no
  one has seen is a Linux `eidolon` creating those directories and a jev
  service finding its record beside its log. *observed source; runtime
  hypothesis.*

### 2.2 Found beyond the list, in order of consequence

1. ~~**The `bonsai2` root is not a git repository.**~~ **Half resolved on
   2026-09-20 — and the half that landed is the one this item argued for.**
   The root is now a repo on branch `master`, with a `.gitignore` covering
   secrets, runtime state, weights, binaries and the nested repos
   (*observed*, `git status`). That switches the fetcher from `path` to
   `git+file` and disarms exactly the hazard below: the 102 GB of models,
   the 71 GB `eidolon/target/`, the 580 MB browser venv and `.webui/`'s live
   database and `.webui_secret_key` are all ignored, so none of them is
   copied into the store.

   **But it has zero commits and every path is untracked**, and this item's
   own citation is what makes that fatal rather than untidy: for `git+file`,
   files are included *"as long as they have been added to the Git
   repository."* Nothing has been. So a flake at the root today does not see
   102 GB — it sees **nothing at all**, which fails differently and reads at
   first like a broken `flake.nix` rather than an empty tree.

   The original reasoning stands verbatim and is now the justification for
   the `.gitignore` rather than a warning about its absence: *a `flake.nix`
   placed at a non-repo root is fetched by the `path` fetcher, which copies
   the directory tree into the store* (*reasoned from the Nix manual: "if the
   flake at path is not inside a git repository, the `path:` prefix is
   implied"*). **`git add -A && git commit` is the remaining step**, and it is
   still a repository decision, not a Nix one.
2. **eidolon cannot be built from git today.** Untracked, build-required
   files include `crates/web/` (the whole crate), `crates/rune/src/ext.rs`,
   `crates/rune/src/warrant.rs`, `crates/tools/src/service.rs`,
   `crates/cli/src/ext.rs`, `crates/cli/src/serve_host.rs`,
   `crates/core/src/ipc.rs`, `crates/providers/src/fallback.rs`
   (*observed*, `git status`). A git-sourced Nix build — `github:` or a
   dirty `git+file:` — omits every one of them and fails at the first
   `mod`. The existing flake builds the 2026-09-16 tree: no extension host,
   no shim, no warrant. S15 already names this ("41 files uncommitted, no
   decision to commit"; it is 73 now).
3. **The existing eidolon flake is stale on `harnox`.** `flake.lock` pins
   `noah427/harnox` at `cbff175` on `embedding-apis`; the tree builds against
   `master` `858f597` **plus** uncommitted S6c changes that add a
   dependency. `cargo metadata --locked` passes against the local patched
   sibling (*observed*), so `Cargo.lock` carries `dirs` for harnox; a build
   whose `../harnox` is `cbff175` does not have it. Whether
   `buildRustPackage` then fails or re-resolves is a *hypothesis*; the fix
   is the same either way: commit harnox, tag `v0.3.6` (the flake's own
   comment says this), and move both the `Cargo.toml` tag and the input.
4. **Both core repositories are private.** Flake inputs by `github:` need
   an access token in `nix.conf` or `git+ssh` URLs on every machine that
   evaluates the lock (*documentation*); jevlike does not.
5. **The face cannot be skinned the way it is skinned now.** hoot.ps1 writes
   into the installed package. In the installed 0.11.3 (*observed*):
   `config.py:97–144` **unlinks every file in `STATIC_DIR` and repopulates
   it from `FRONTEND_BUILD_DIR/static` at import**, then copies `favicon.png`,
   `splash.png` and `loader.js` again from the frontend; `main.py:2989`

   the environment. In nixpkgs, the `open-webui` wrapper is
   `--set FRONTEND_BUILD_DIR ${frontend}/share/open-webui` — `--set`, not

   `STATIC_DIR` and `DATA_DIR` under a state dir, `HOME` and
   `WorkingDirectory` to it, `DynamicUser`, and `ProtectHome` among a long

   `env.py` patch, cannot be done at launch there at all (R7).

    project's checkout; the trained one is in a session scratchpad. Both

12. **`providers/hoot.rn` is seeded by hand.** Nothing in hoot.ps1 copies
    `providers/` into eidolon's config dir; the Build-Log shows the

    (*observed*). S13 is the same hole for `extensions_dir`.
13. **`bash` on NixOS.** `posix_fallback_paths()` is `/bin/bash`,
    `/usr/bin/bash`, `/usr/local/bin/bash`, documented in the code as
    reasoned (*observed source*). None exist on NixOS, which has `/bin/sh`
    and `/usr/bin/env` only (*documentation*). `bash` on `PATH` and
    `EIDOLON_BASH` both work; a Nix wrapper for the binary should set the
    second.
14. **Extension services versus a service manager.** On unix eidolon
    starts a service under `setsid` (its own session and process group)
    and kills it with `SIGKILL` to `-pid` (*observed source*). A service
    is designed to outlive the session that started it and be adopted by
    the next (`docs/extensions.md`). Under systemd, a child in the shim's
    cgroup dies with the unit unless `KillMode=process` is set — which
    inverts the design, or the hardening, depending on which is chosen
    (*documentation*). This is why R4 does not rule systemd units for
    stage one.
15. **`system.rs` writes to the config dir on every launch**, `--config`
    notwithstanding (S32) — incompatible with `ProtectHome` and with any
    read-only home. A unit for the shim must not use that hardening.
16. **`Get-WebUI` would stop another project's Open WebUI.** It matches
    any python process whose command line mentions `open-webui`
    (*observed*), the loose-identifier shape Decisions already condemned
    for the shim. The POSIX launcher must own what it starts by pidfile
    (R4); Windows keeps its behaviour, noted.
17. **`WEBUI_NAME_SUFFIX` is a hoot patch, not an upstream feature.** The
    installed `env.py:937` carries the patched conditional because hoot.ps1
    wrote it there; nixpkgs applies no such patch (*observed +
    documentation*). On Nix it is an `overrideAttrs` `postPatch` or the
    suffix is accepted.
18. **The training set is outside every repository and should stay there.**
    `scripts/get_wikispeedia.sh` needs `curl`, `tar` and `jevlike-data`
    (*observed*); the SNAP archives are public, content-stable tarballs and
    can be fixed-output inputs if reproducibility of the *data* is ever
    wanted; the split is by target hash (judgement.md §1).
19. **The Vulkan verdicts are Windows-driver verdicts.** Every CPU-versus-
    Vulkan decision in `models.ini` was measured against AMD's Windows
    driver; a Linux box drives the 860M through Mesa RADV. Whether each
    verdict holds is *hypothesis*, and `models.ini`'s `n-gpu-layers` lines
    are the ones that would move.

## 3. Rulings

### R1. What the flake is for: both, staged — and stage one is a dev shell whose layout is already stage two's

**Stage one** is a `flake.nix` at the `bonsai2` root whose only outputs are
`devShells` — `default`, `serve`, `train` (R2) — over one pinned `nixpkgs`
plus one input, `jevlike`. It provides toolchains and services from the
store and runs the tree **in place**: `cargo build` in `eidolon/` against
the on-disk `../harnox`, extensions from `extensions/`, models from
`models/`, the launcher from `bin/`. Nothing about eidolon is built by Nix
in stage one; `eidolon`'s own flake is left alone until stage two.

**Stage two** is `packages` and a module: `eidolon` by composing
`eidolon/flake.nix` as an input (never re-implemented at the root), the two
extension services as Python environments plus source, the skinned face,
the launcher, and a home-manager module of user units generated from the
same declarations the launcher reads; plus `checks`, which is S15's CI.

**Why staged in this order.** Stage two has four preconditions that are not
Nix work and not mine to decide: eidolon committed (item 2), harnox
committed and tagged (item 3), the root under git (item 1), and a token or
ssh route for two private inputs (item 4). Stage one needs only the third
and a Linux box. It also delivers the one property the operator named as
the reason for Nix — *a checkpoint trained against a different torch is a
silent behaviour change* — because a `train` shell and a `serve` shell from
the same `nixpkgs` revision carry the same torch on both machines (R9).

**What stage one must not preclude**, each a constraint on how the dev
shell is written:

1. The flake lives at the root and the root is a git repository from the
   first commit, with the ignore list in spec step 0.3. A `nix/` sub-flake
   without git would work for a shell and would have to move for packages;
   moving a flake changes every invocation and re-locks everything.
2. Every machine-specific location is an environment variable with a
   repo-relative default, resolved in one place per language, named now
   (the contract table in the specification). Stage two's derivations set
   them to store paths; stage one's shells set them to store paths where
   the thing is in the store and leave the default where it is on disk;
   Windows sets none and behaves as today.
3. The launcher is parameterised by binary paths and never discovers
   them beyond PATH and its own defaults, so a store path can be handed to
   it without the script knowing what a store is.
4. `models.ini` is relative to the router's working directory and the
   launcher fixes that directory (R6).
5. The root flake never takes `./eidolon` as a `path:` input — a `path`
   fetch copies `target/` (71 GB) before any filter can run. eidolon
   enters stage two as `github:noah427/eidolon` (with `--override-input`
   to a `git+file:` URL for local work), and `harnox` enters through
   eidolon's flake, as it does today.
6. Checkpoints are repository content, in-tree (R3), so a derivation can
   read them.

### R2. How many machines: one flake, three shells now, one runtime module later; the training box needs no GPU for anything on the board

One flake, one `nixpkgs` revision, several outputs. What each contains:

| output | machine | contains | does not contain |
|---|---|---|---|
| `devShells.default` | this laptop, or any dev box | rust toolchain (cargo, rustc, clippy, rust-analyzer, `RUST_SRC_PATH`), python env **A** for jev (torch CPU, numpy, transformers, safetensors, fastapi, uvicorn, pytest), python env **B** for the browser (playwright, fastapi, uvicorn, pytest, httpx2 if packaged), `playwright-driver.browsers` with only Chromium, `llama-cpp` with `vulkanSupport = true`, `open-webui`, `bash`, `curl`; the environment contract set to store paths | any model file; any checkpoint built by Nix |
| `devShells.serve` | a box that only runs the stack | everything above minus the rust toolchain; `eidolon` from PATH or `HOOT_EIDOLON` (stage two: from the eidolon input) | rustc |
| `devShells.train` | the second machine | python env **A** minus fastapi/uvicorn, the `jevlike` input on `PYTHONPATH`, `curl`, `gnutar`, `OMP_NUM_THREADS` unset so the operator sets it per box | llama-cpp, Chromium, Open WebUI, torch with CUDA (below) |
| `packages.*` (stage two) | | `eidolon` (via input), `hoot` (the launcher, wrapped with the contract), `jev-service`, `browser-service`, `webui-skinned` (R7) | models |
| `homeManagerModules.hoot` (stage two) | a Linux laptop running the stack daily | user units for router, shim, face; `KillMode=process` on the shim or the open question in item 14 resolved first | `ProtectHome` (item 15) |
| `checks` (stage two) | CI | eidolon's suite via its flake (`doCheck` already on), `jev/tests`, the browser tests that do not launch Chromium | tests that launch Chromium, until the sandbox question in §6 is settled |

Two shells share env **A** so that the checkpoint trained in `train` is
scored in `serve` by the same interpreter and the same torch, byte for
byte. That is the whole design of the machine split.

**CUDA is off until an experiment that needs it is scheduled.** The model
on the board is 41,280 parameters trained in 12.5 minutes on eight
contended CPU threads (*observed*). A CUDA torch is unfree and not in the
official cache, so it is a multi-hour source build per revision
(*documentation*); `torch-bin` is the prebuilt escape hatch when the day
comes. The one experiment on the board that would want a GPU is C6, the
frozen 0.5B encoder, and judgement.md already records the README's number
for it as *worse* than the byte model on this data (26% against 29%).

### R3. Models: the flake never sees a gigabyte

Three classes, three homes.

**GGUFs and openjev — 102 GB.** They stay in `models/` at the root,
gitignored, outside the flake's source, and are addressed by exactly one
convention: `models.ini` names them relative to the repository root and
the launcher starts the router there (R6). A box whose models live on
another disk makes `models/` a symlink (a junction on Windows). They are
never a flake input, never a fixed-output derivation, never copied into
the store: a fixed-output fetch of 18 GB duplicates the file, roots it
against GC, and buys reproducibility for a file whose identity is already
a URL and a size. What replaces content-addressing is a manifest:
`models/MANIFEST.sha256`, generated once here (`sha256sum` under Git Bash)
and checked by `hoot models --verify` on any box, so "the same model" is a
claim a second machine can test before benching against it. Transfer is
`rsync` or a disk, not Nix's business.

**Chooser checkpoints — 169 KB each.** Repository content, tracked in git
at `extensions/jev/checkpoints/<name>.pt` with the calibration record S47
specified beside it, and `JEVLIKE_CKPT` defaulting there. A checkpoint
trained on the second box "comes home" by `git push`, with the record that
says what torch and what platform produced it (R9). `synthetic.pt` moves
in from the jevlike checkout (it was never that repository's content);
`wikispeedia.pt` moves in from scratch under the name the record gives it.
Until the calibration record lands (judgement.md step 1), the record is a
sidecar text file with the fields named in R9.

**Training data — hundreds of MB.** Outside every repository, as today,
produced by `scripts/get_wikispeedia.sh` from public SNAP archives. If the
*data* ever needs to be reproducible, the two archives become fixed-output
inputs (they are content-stable tarballs), and that is a stage-five nicety,
not a requirement.

### R4. The launcher becomes a POSIX `bin/hoot` in bash beside `hoot.ps1`; not systemd units yet; and eidolon keeps owning extension services

Four candidates were on the table.

**eidolon itself** (`eidolon up`) — rejected. Hoot.md fixes the geometry:
eidolon is a component of Hoot, not its owner; the router and the face are
not eidolon's; and the part of the launcher that *is* eidolon's — starting,
adopting, health-checking and stopping extension services — eidolon already
does through `ext start`/`ext stop` and on every `serve`. The launcher
already defers to it (hoot.ps1 `stop`: "an extension service the shim
started is eidolon's to stop"). That boundary holds on Linux unchanged.

**systemd user units** — the right shape for stage two's daily runtime and
the wrong first move. Idempotent `up` is systemd's native behaviour and
ordering is `After=`; but item 14 (services in the shim's cgroup) and item
15 (`system.rs` versus `ProtectHome`) each need a decision that a Linux box
has to inform, and a unit set is not testable from here at all. It becomes
the home-manager module in stage two, generated from the same declarations
the script reads, once a Linux run has shown where the services end up.

**A Nix process manager** (process-compose and kin) — rejected as a third
supervisor to learn for a stack whose supervision is 200 lines of probe,
start, wait and stop.

**A bash sibling** — ruled. Same verbs, same order, same waits, same
registration as hoot.ps1; owns its processes by **pidfile** under
`$XDG_RUNTIME_DIR/hoot/` (falling back to `$XDG_CACHE_HOME/hoot/run`), each
pid re-checked against `/proc/<pid>/comm` before it is trusted and before
anything is stopped — the rule from "a launcher may only stop what it can
prove it started", applied to the third process too (item 16); probes by
`curl`; binaries from the contract variables, else PATH; logs in `logs/`
as today; the skin in one of two modes (R7); `setup` = seed
`providers/hoot.rn`, `eidolon ext dir`, and print what `extensions/jev/env.sh`
needs (R5).

The two scripts share no executable line and **must share the
declarations**: ports, the Open WebUI environment including the
index-keyed `OPENAI_API_CONFIGS` headers, `TASK_MODEL_EXTERNAL`, the
banner. S11's lesson — two copies with nothing binding them — is answered
the way S11 proposes: not a third parser of one file, but a **test that
the two agree**. Both launchers gain an `env` verb printing the exact
environment they would hand Open WebUI, token redacted, and a Git Bash test
diffs them with path-valued keys normalised (spec step 2.6).

Considered and deferred: making the bash script primary on Windows too,
since Git Bash is already a hard requirement of eidolon there (S34). It
would give one launcher tested on both platforms. It is a bet on MSYS2's
background-process and kill semantics that nobody here has observed, taken
against a launcher four agents are using today; §6 lists the trial that
would settle it.

Three Windows-side changes are needed for parity and each is testable
here: the router's working directory (item 9), the face's working
directory (item 6), and seeding `providers/hoot.rn` in `setup` (item 12).
None changes what a Windows operator types.

### R5. jevlike: a declared input by revision; `JEVLIKE_ROOT` required with a startup refusal; the interpreter named per machine in the extension's own directory

- **Code.** `github:vinnylarouge/jevlike` pinned to `94f5fd1`, `flake =
  false`, which is what `JEVLIKE_ROOT` points at under Nix. On Windows it
  stays the sibling checkout and `JEVLIKE_ROOT` names it. Not vendored:
  `server.py`'s own comment says why, and the repository is public and
  small. Not packaged: it imports fine from a directory on `sys.path`, which
  is how `server.py` already reaches it, and a `pip`-style package would be
  a second way to do the same thing.
- **The variable.** S48's fix, sharpened by where the failure surfaces:
  `JEVLIKE_ROOT` has **no default** and is checked **at import**, with the
  same `is_dir()` test `_jevlike()` runs now, so a mis-set box fails when
  `eidolon` starts the service — in the service log the extension host
  already shows — and never at the first `choose`. The check costs a `stat`
  and imports no torch, which keeps `/health` what it is. `OPENJEV_DIR`
  defaults to `<repo>/models/openjev` derived from `__file__` exactly as
  `GRAPHS_DIR` is, overridable. `JEVLIKE_CKPT` defaults in-tree (R3).
- **The interpreter.** D9's settings map is the designed fix and is not
  landed. The interim that works on both platforms today and needs no
  eidolon change: `service.command` sources an optional, gitignored
  `{dir}/env.sh` and then runs `"${JEV_PYTHON:?…}" -u server.py`, where
  the `:?` message names the variable and the file — bash's own way of
  failing by name at spawn, which is D9's shape one layer later than D9
  wants it. `env.sh` is per-machine content in a directory the operator
  already owns (the extension dir, pointed at by `ext dir`), the same way
  the browser extension's `.venv` is per-machine content in its directory.
  Under Nix `env.sh` is absent and `JEV_PYTHON`/`JEVLIKE_ROOT` arrive from
  the shell that started `eidolon`. When D9 lands, the same two names move
  into `[[extensions]]` settings and `env.sh` is deleted; the test in spec
  step 1.3 is written against the names, not the mechanism.

### R7. The face on Linux: the same package, the skin applied where the platform allows

Two modes in one launcher function, selected by whether
`HOOT_WEBUI_FRONTEND` is set:

- **in-package** (a `uv tool` install, on Linux as on Windows): copy
  `webui/custom.css`, `webui/brand/*`, the rewritten `loader.js` into the
  package's `static/` and `frontend/static/`, patch `env.py` and
  `frontend/index.html` — hoot.ps1's five actions, with the site-packages
  path taken from `uv tool dir` rather than a literal (`Lib\site-packages`
  on Windows, `lib/python3.*/site-packages` on POSIX).
- **overlay** (Nix): assemble a writable copy of `${HOOT_WEBUI_FRONTEND}`
  under `$XDG_STATE_HOME/hoot/webui/frontend` — a symlink tree plus real
  files for the three overlaid ones and the patched `index.html` — set
  `FRONTEND_BUILD_DIR` to it and `STATIC_DIR` to a sibling writable
  directory, and let Open WebUI's own import-time copy (item 5) populate
  `/static` from the overlay. The store is never written. The `env.py`
  suffix patch cannot be applied this way; in stage three the suffix is
  accepted, and in stage two it is an `overrideAttrs` `postPatch` on the
  same package that also replaces the wrapper's `--set` with `--set-default`
  so the overlay can be handed in through the environment.

Both modes keep the two launch-time facts in `loader.js` — `SHIM_ORIGIN`
and the live `/jev` probe — because the overlay is rebuilt on every `up`,
which is exactly what hoot.ps1 does with the in-package copy today.

`DATA_DIR` stays `<repo>/.webui` in stage one for parity; the face's
working directory becomes `DATA_DIR` on both platforms so the app's own
`.webui_secret_key` lands beside its database (item 6; the NixOS module
does the same with `WorkingDirectory = stateDir`).

### R8. Platform as a parameter, applied to the new code

Every piece of new logic that has a platform branch takes the platform as
data and is tested on both branches here: `chromium_installed(browsers_path,
package_dir, platform)` replacing the current globber; the launcher's
`detach`/`alive`/`stop` primitives behind functions a Git Bash test can
stub; `env.sh` presence and absence exercised by running `bash -c` with the
manifest's own command string. Nothing new uses `cfg!`, `sys.platform`
read at the point of use, or `$IsWindows` inside logic. The existing
`_paths.cache_dir()` is the model.

### R9. Training and the second box: a view, with its evidence

The operator's own framing survives inspection and gets sharper.

*What the 12.5 minutes were.* CPU, eight threads, three other agents
building, four epochs, `--device cpu` (*observed*, judgement.md). Eight
epochs is about twenty minutes here. The checkpoint is 169 KB; inference
is 2.5 ms; nothing about a faster box changes either number.

*So the second machine buys isolation, not capability.* This laptop's
binding constraint is memory pressure, measured: gpt-oss at 3.3 tok/s
against its benched 12.21 with two models resident and three builds live
(Build-Log, "Why the bench still has not run"). A twenty-minute
eight-thread training run on the laptop is another tenant in that fight.
On the second box it costs the laptop nothing, and what comes home is a
file smaller than this document. Concretely better there: more epochs
(validation NLL still falling), several domain checkpoints in parallel
(A8: browse, directory, shell), the 512-byte context variant (C5), and
hyperparameter sweeps — all CPU work at this model size.

*What it does not change is what is worth training.* Sizing is argued
against 2.5 ms and the laptop's memory, not against the second box's. A
checkpoint over a few megabytes needs a stated reason. The frozen-encoder
path (C6) is the one thing that would want the GPU, and it is also the
thing that would put a 0.5B encoder resident on the laptop per call —
the "has to come home" constraint, exactly where it bites.

*Reproducibility is the real link to Nix.* `train` and `serve` from one
`nixpkgs` revision give one torch on both boxes, closing "trained against a
different torch" by construction. Two things make it checkable rather than
believed: the calibration record (or its sidecar until it lands) carries
`torch.__version__`, the platform triple, the `nixpkgs` revision when
known, and the checkpoint's sha256; and every import of a checkpoint is
accepted by re-running `jevlike.eval` on the laptop and matching top-1 and
ECE to the record within a tolerance that §6 asks the Linux box to
establish. Today's torch here is 2.14.0 and nixpkgs' is 2.13.0; a
checkpoint crossing that gap is the first thing the parity test measures.

*One temptation to name.* Serving openjev — the four-orders-of-magnitude
guard — from the faster box would be the obvious use of it. The extension
host refuses any endpoint that is not loopback, by design and for the
right reason (a bearer token on the network). A tunnel to loopback is the
only door and it is a design change to the service contract; not ruled
here, only noted.

## Implementation specification

Five stages. Stages 0–2 are executed and proven on **this Windows box**;
stage 3 is written here and proven on a Linux box; stage 4 needs R10's
four gates and a Linux box; stage 5 is the second machine. Each step names
the tree it touches, the test that proves it, and — where Windows cannot
prove it — the letter in §6 that does. Test names are the names to use.
Nothing here is Nix code; the stage-3 and stage-4 steps describe what the
flake must contain and how it is checked, not how it is spelled.

**Isolation, always.** Any step that runs `eidolon` runs it with `--config`
at a scratch path and, for jev, with the four `JEV_*` isolation variables
judgement.md names; production `decisions.jsonl` is hashed before and after
(the rule J2 wrote by breaking it). No step edits the operator's
`config.toml` except through `eidolon ext dir`.

root, which is the directory above `bin/`.
