### input-1 (low): Unknown-chat start does an uncapped full sessions listing on every request

`perch/src/runs/state.rs`

A bearer holder, or a page that retries a tagged start after its 404, POSTs /hub/runs with a well-formed chat id that is neither remembered nor listed (for example 128 letters). Each POST reaches chat_known (line 622), which calls registry.list() because known_cwd misses. list_at (sessions.rs:806) then reads the sessions dir and eidolon's read-only other dir (titles::logs_in, titles.rs:239-249, one stat per .eid), reads every runtime roster meta.json (sessions.rs ~911) and runs kill(pid,0) on each, with no cache and no cap on file count. Each request holds a spawn_blocking thread for that walk. The RT.json lens asks for no unbounded directory walk per request, and this is one for every unknown id. The cost is bearer-gated and close to what GET /hub/sessions already costs, so the severity is low. The term twin (term/routes.rs:145-156, 104-115) has the same shape, so this is shared. serve.rs:709-728 shows the codebase's own bound for listings (tree::MAX_LISTINGS slots), which RT does not use.

- Fix: Answer membership with single lookups before falling back to list(): log_path(sessions_dir, id).is_file(), log_path(other, id).is_file() when other is set, and the door table by id. The door lookup is required because a door can exist with no log yet (Ours.log is an Option). Alternatively take a slot like tree::MAX_LISTINGS. Keep the term twin in step.
- Verify: The mechanism is real. An unknown well-formed chat id reaches create() and chat_known (state.rs:578, 621-622). known_cwd (sessions.rs:532-534) finds nothing for an unremembered id, so the code falls through to registry.list() (sessions.rs:796-806). list_at reads the sessions dir and eidolon's other dir (titles.rs:239-249, one metadata stat per .eid), reads every runtime roster meta.json with a kill(pid,0) per row (sessions.rs ~890-915), and has no cache and no file-count cap. The walk needs the bearer or the perch's session cookie (serve.rs authenticated ~279; /hub is gated), and cross-site pages are refused by the Sec-Fetch gate. The finding omits the comparison that sets the severity. GET /hub/sessions (serve.rs:660) calls titled_list (sessions.rs:700-703), which can spawn `eidolon sessions` (titles.rs:724, 10 s cap) and then runs list() synchronously on the reactor with no slot. Two corrections: the 'RT.json lens' asking for no unbounded walk is not in RT.json, pass2-final.json or BRIEF.md; RT.json's own risk entry accepts the per-start directory reads under spawn_blocking. And tree::MAX_LISTINGS (serve.rs:709-728) bounds only /hub/tree, not /hub/sessions or term's twin. The defect is real and the spec accepted it, so low (defence in depth), not higher.

### input-2 (info): POST /hub/runs silently ignores any query string, including a chat= query

`perch/src/runs/state.rs`

route() (line 496) sends Verb::Create to create(), which never reads req.uri().query(). So POST /hub/runs?chat=../x with a body that has no chat key is accepted (202) as an untagged run, with no refusal. There is no security effect: the query is never used, nothing is joined or stored, and it matches the spec's 'other verbs ignore the query'. The spec's 'every shape that is not a chat id is refused' is only enforced on GET ?chat=. A client that puts the chat in the query string on POST silently loses its tag.

- Fix: None required. Optionally refuse a non-empty query on POST, or say in the README that the start's chat is read from the body only.
- Verify: The observation is accurate and by design. create() takes the request and reads only the body through object() (state.rs:538-545), and route() passes the query only to list() (state.rs:495). So POST /hub/runs?chat=... is accepted as an untagged run with 202 and no refusal. RT.json says other verbs keep ignoring the query, and serve.rs seam() (593-594) routes by path only. The query is never joined to a path, stored or sent to eidolon, so there is no security effect. A contract note for the page author, nothing more.

## Rejected

- **leak-3**: A new chat that reuses a deleted chat's id inherits that chat's tagged runs (operator-accepted as U7). Not reachable under normal operation, so the failure scenario cannot be shown to happen. eidolon names a new chat's log '<ms>.eid', with a '-n' suffix only on a same-millisecond collision, and creates it with create_new (eidolon crates/cli/src/config.rs:611-630). The id is therefore the creation millisecond. For a new chat Y to get deleted chat X's id, Y must be created in the same millisecond X was created, while X is already gone (if X still existed, Y would take the '-n' suffix). With a monotonic clock that means creating X, deleting it and creating Y within one millisecond, which is not possible through the HTTP or trash flow. The only route is a backward clock step that lands exactly on X's millisecond, and no such trigger is shown. The no-cascade mechanism is real (no code removes a deleted chat's tagged runs), and RT.json accepts id reuse as U7, so no separate defect remains. Forks (fork.rs) use the same millisecond-based naming.
