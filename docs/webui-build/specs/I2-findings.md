# R4 review findings routed to I2 (installer key hardening)

## arm-2 [low] installer/src/keys.rs:410
Revocation is by key id only, so a revoked key's bytes pass the perch's add under a fresh id with the same fingerprint
SCENARIO: state.json revokes R (id 78D2AE5B2ECB3ECA). The perch's add argv with R's own .pub answers 409 revoked. I re-wrapped the same 32 key bytes with a fresh id (1DDC9858FFDCF3F0) and sent --confirm with the unchanged fingerprint 35DA57C2C0913B15. Result: {"added":"1DDC9858FFDCF3F0"}, trusted, 'added by hand' (probe with master's minerva, temp HOME). Suppose a release key leaked and was revoked, and the maintainer once published its fingerprint. That key then passes the person's out-of-band fingerprint comparison, and the attacker's secret signs under the new id (minisign-verify only matches the key id to the pubkey's own id). The perch cannot catch it. commit_rotation deletes a revoked key's files (keys.rs:628), so `keys list --json` has no fingerprint for it. This already exists on master through the CLI; R4 adds a path from the page.
FIX: I1: record the fingerprint of each revoked key (sha-256 of its 32 bytes) in state.json. Refuse add_manual and rotation adds by fingerprint as well as by id, and filter trusted() by revoked fingerprints. Once the list or state exposes revoked fingerprints, R4 can apply the same refusal at the arm or add step.

## process-beside-overrides-flag [low] perch/src/install/mod.rs:213
A minerva sitting next to any perch binary silently overrides an explicit --minerva, including in a cargo target dir that already holds a real installer build
SCENARIO: resolve() (mod.rs:208-219) takes `<canonical exe dir>/minerva` whenever it is executable and only then looks at the flag. The unit test at mod.rs:887 locks that order in. A cargo target dir counts as an exe dir, and installer/src/bin/minerva.rs builds into one. On this box `~/.cache/minerva-master-target/debug/` already holds both `perch` and a real debug `minerva` (built 14:08). I ran a probe in $HOME/.cache/minerva-review-R4/probe on port 48111: I copied the R4 perch and that real minerva into one dir, passed `--minerva <fake_minerva>` and used temp HOME/XDG. GET /hub/install returned `{installed:true, version:"0.1.0-g02ac6ee", ...}`, which is the real installer answering. GET /hub/install/keys returned `[]`, and fake_minerva wrote no log at all. Three effects: (1) once merged, `cargo test --features test-bins` in master-target runs the real minerva in place of the fake. `without_a_minerva_...` and every fake-backed test then fail, and README.md:124 ('No test runs a real minerva') is false there. (2) The R4 live check on 48111 ('fake_minerva in installed and not-installed modes'), run from that target dir, can show neither mode; it drives the real installer. (3) That real binary inherits HOME and XDG_CONFIG_HOME from the perch. A dev or live-check perch started with the operator's own env therefore lists the operator's real ~/.config/minerva/update-keys, and an armed remove of an 'added by hand' key there deletes a real trusted key. The person believes they are exercising the fake.
FIX: Take the beside binary only when the perch is an installed copy: its canonical exe must have the shape `<prefix>/opt/minerva/<ver>/bin/perch`, the same check installer Layout::from_exe does. Otherwise use only --minerva. Another option is to let an explicit --minerva win over the beside binary. Update the unit test at mod.rs:887, and add a test where a stray `minerva` sits next to the test perch. Fix the README claim either way.

## process-fake-misstates-real-remove [info] perch/src/bin/fake_minerva.rs:20
fake_minerva says the real program refuses to remove rotation keys; it does not, so the perch's list check is the only guard for ruling 6
SCENARIO: The fake's doc says 'Unlike the real program the fake lets remove take a rotation key out'. The real Trust::remove (installer/src/keys.rs:425-438) refuses only Source::Compiled, and keys_remove (installer/src/bin/minerva.rs) adds only the --confirm fingerprint check. So `minerva keys remove <rotation-id> --confirm <its FP> --json` removes a rotation key. The test at tests/install.rs:559 is correct and does prove the perch refuses. A later slice reading the fake's doc, though, would assume minerva backs that refusal up. In fact mod.rs:689-706 is the sole enforcement, and it is a check-then-act: the source is read from `keys list`, then `keys remove <id>` re-reads the dir. If that check is weakened, or a key's .json source changes between the two runs, a rotation key goes.
FIX: Fix the fake's doc to say the real program also removes rotation keys and that the perch's source check is the only guard. Keep the fake's permissive behavior, since it is what makes the test meaningful. Optionally ask the installer to refuse non-manual removals under --json (as an upstream contract item), so the guard exists on both sides.
